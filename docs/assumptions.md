# Допущения MVP

Поскольку уточняющие вопросы к заказчику не задавались, ниже зафиксированы явные допущения прототипа.

## Допущение 1. Лимит переговоров

В MVP ограничение: **максимум 50 переговоров в день** (настраивается).

## Допущение 2. Capacity менеджеров

Если точный индивидуальный график неизвестен, для демо используется одинаковая базовая capacity: **10 переговоров на менеджера**.

Алгоритм **не жёстко привязан** к 10: архитектура поддерживает разные индивидуальные лимиты.

## Допущение 3. Состав новой заявки

Минимум для демо: ID, дата, регион, продукт.  
Дополнительные поля (источник, тип клиента, срочность, бюджет) — экспериментальные.

## Допущение 4. Синтетические данные

Реальные данные компании отсутствуют → используются **синтетические демонстрационные данные**.  
Это явно показано в интерфейсе и документации.

## Допущение 5. Нет data leakage

Историческая информация используется только в объёме, известном **до** момента назначения заявки (`date < as_of`).  
Фильтр централизован в `historical_data()` и применяется в scoring / baseline / form.  
Факт будущей продажи, GM и скидка новой сделки в признаки назначения не входят.

## Допущение 6. Целевая метрика

Оптимизируется **ожидаемая валовая маржа (GM)**, а не число обработанных заявок само по себе.

## Допущение 7. Основная модель

Прозрачная статистика (сглаживание + свежесть + fallback), не нейросеть.  
ML возможен как следующий экспериментальный этап.

## Допущение 8. Найм

Модуль capacity/экономики найма — **этап 2 / стратегия**.  
Система не утверждает, что «нужно срочно нанять менеджера».
